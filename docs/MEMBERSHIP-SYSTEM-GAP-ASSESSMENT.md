## 0. 一句话结论

**文档描述的三层需求（计费规则 / 后台 8 模块 / 用户端 5 模块）在当前代码库中几乎为零实现**，但项目已具备落地所需的全部底座（鉴权、任务生命周期、资产库、模型提供商多供应商故障转移、Redis 并发闸门）。

真正的难点不是页面数量，而是三件事：

1. **积分账本与任务生命周期的对账闭环**；
2. **限时积分的过期清零**（需要独立调度器）；
3. **会员并发等级的改造**（现有闸门是 provider 维度，不是用户维度）。

**风险最高的不在代码，而在数据本身**：

- ~~三套互斥的会员定价~~ **已定（2026-09-17 用户确认）：只开 ¥198 / ¥1980 两档付费会员，新用户注册赠 1000 积分**；截图中的 4 档结构与 ¥129/¥419/¥839 全部废弃。各档权益数值仍由后台套餐配置承载（文档正文自述「具体权益可参考…根据我们平台有的调整」），不硬编码；
- 原型截图里的扣费数值与官方定价页互相矛盾，**不能当验收基准**——§6；
- 账号池仍是上线前置条件——§2.5。

| 需求 | 现状 | 差距 |

关键设计约束（来自项目硬约束「先保证不丢数据、不卡死」）：

## 3. 复用 vs 新建（投入结构）

```
可复用（约 20%）  鉴权 / Job 状态机 / 幂等键 / 资产库 / 监控面板 / 故障转移
需改造（约 20%）  provider 闸门→用户维度并发 / 管理员三级权限 / User 模型 / 注册流程
纯新建（约 60%）  积分账本 / 过期调度 / 结算对账 / 订单支付 / 邀请 / 审计 / 全部前端页面
```

**两个新基础设施必须先立**（否则后续全是返工）：

1. **过期与结算调度器** —— 当前代码库里没有任何 cron/定时结算组件，只有若干 `Start*Maintenance` 形制的 in-process goroutine（如 `assetService.StartTrashMaintenance`）。31 天积分清零需要一个可靠的定时任务，且要能在多副本下只跑一次。
2. **统一「任务终态 → 账本」消费者** —— 结算必须**幂等**（同一 Job 结算两次不能双扣/双退），幂等键落在流水表唯一索引上。

## 4. 建议依赖顺序（哪些能并行）

```
P0  data model + 账本引擎（冻结/结转/退款/过期）
     |
     +--> P1 结算对账消费者 + 过期调度器          [串行，最高风险]
     |
     +--------------+---------------+---------------+
     |              |               |               |
P2a 会员并发权益   P2b 后台只读面板   P3  邀请体系    P5 支付网关
    (动 worker)    (流水/消耗/看板)   (可独立)      (需产品定渠道)
     |              |               |               |
     +--------------+---------------+               |
     |                                              |
P4  后台写路径（套餐配置/手动调账/退款/审计/权限分级） <-- 依赖 P5 的订单模型
     |
P6  用户端会员中心 5 页
     |
P7  活动与限时折扣配置 + 风控（防刷邀请/防超扣）
```

- **P2b / P3 可与 P1 并行**，它们只依赖 P0 的数据模型。
- **P5 支付网关是外部依赖，必须先有产品决策**，否则订单模块的字段设计会返工。
- **P6 必须在 P1 之后**，否则前端拿不到可信余额。

## 5. 待产品决策（阻塞项）

以下不澄清就会导致返工。**前 4 项由截图数据新暴露**，优先级最高：

### 5.1 定价三套数字互斥 —— ✅ 已解决（2026-09-17）

## 7. 已确认的规则清单（据以实现）

> 完整数据见 **`docs/MEMBERSHIP-SYSTEM-PRICING-DATA.md`**（19 张截图逐张提取，含置信度标注与冲突汇总）

**基础规则**（来源：正文 + `image18` 定价页，两者一致 ✅）

- 兑换基准 **1 元 = 100 积分**（9,800 档为 110/元 优惠例外），活动可调。
- 会员月发积分 **31 天有效期，到期自动清零**。
- 现金直购积分 **永久有效、不清零、可叠加**。
- 活动赠送积分 **自定义有效期（如 30、90 天）**。
- **扣费优先级：优先扣限时会员积分，耗尽后扣永久直购积分**。

## 9. 验收命令（交付前必跑）

```powershell
cd apps/api; go build ./...; go vet ./...; go test ./...
pnpm --filter ai-manhua-studio check; pnpm --filter ai-manhua-studio test; pnpm --filter ai-manhua-studio build
cd apps/worker; python -m compileall worker; python -m unittest discover -s tests
```

账本相关工单需额外覆盖的验收场景：

1. 并发扣费不超扣（同用户多任务同时提交）
2. 重复结算幂等（同一 Job 结算两次不双扣/双退）
3. 过期清零不重复执行（多副本同时跑）
4. 限时优先扣减：限时余额充足时不消耗永久积分；限时耗尽后自动转永久
5. 会员到期：特权失效 + 限时积分清零，**永久积分余额不变**
6. 退款回滚到「限时积分已过期」场景（按冻结时刻快照决定回滚目标）
7. 强制扣费失败时任务不得进入成功态（不丢数据、不卡死）
8. 邀请奖励在「未首充」时保持「待发放」，不得提前发放
